Inspecting 50,000-File Delta Lake Tables in 111ms & 89MB RAM Without a JVM

Engineering notes & reproducible benchmarks for deltalens v2.0.1 (MIT · Rust)

Every data engineer working with Delta Lake has hit the same papercut: you just want to know whether a table has a small-file problem, how much storage is sitting in expired tombstones, who ran the last MERGE, or whether a PR introduced a breaking schema change — and your choices are booting a 15-second Spark session, paying for a Databricks SQL warehouse, or wrangling a Python virtualenv with deltalake.

DeltaLens is a standalone, strictly read-only Rust CLI & library (13.8 MB) that reads only _delta_log/ metadata — NDJSON commits, classic & multi-part Parquet checkpoints, V2 checkpoints with _sidecars/, .compacted.json logs, Deletion Vectors, Column Mapping, and Liquid Clustering — across local disks, S3, GCS, and Azure ADLS.

Four Architectural Decisions That Make It Fast (and Safe)

1. _last_checkpoint Offset Listing for Cloud Stores

Listing _delta_log/ on a busy S3 table with 50,000 historical commits burns dozens of paginated ListObjectsV2 calls before you even read a byte. For snapshot and diff queries, DeltaLens reads _delta_log/_last_checkpoint first and invokes object_store::ObjectStore::list_with_offset starting at {V:020} — collapsing dozens of listing pages into one, with automatic fallback to a full single-pass inventory when inspecting pre-checkpoint history or stale hints.

2. Strict I/O vs. CPU Concurrency Split (Zero Nested Tokio Runtimes)

Cloud object fetches run over a shared process-wide Tokio runtime using futures::stream::buffer_unordered(32). Once raw bytes are in memory, NDJSON commit and Arrow/Parquet checkpoint parsing fans out across Rayon worker threads. Rayon workers never enter rt.block_on(...), eliminating runtime starvation and deadlock classes.

3. Unified Remove-Before-Add Replay State Machine

Operations like RESTORE and Deletion Vector updates emit both a remove and an add for the same physical Parquet path inside a single commit. DeltaLens keys active files by (percent_decoded_path, deletion_vector_unique_id) and executes Phase 1 (Remove) strictly before Phase 2 (Add) within each commit, while tracking delta.deletedFileRetentionDuration to compute exact reclaimable tombstone bytes.

4. Read-Only & TOCTOU-Free Local Containment

The StorageBackend trait exposes no write, delete, or rename methods. On Linux/macOS, LocalStorage pins the table root via O_DIRECTORY | O_CLOEXEC and walks every relative component with openat(..., O_NOFOLLOW). V2 checkpoint _sidecars/ references and cloud keys reject traversal segments (.., backslashes, NUL bytes, prefix escapes).

Using DeltaLens as a 5-Line GitHub Actions CI Gate

- uses: sandy-sachin7/deltalens@main
  with:
    command: diff
    path: s3://my-bucket/warehouse/transactions
    args: --v1 ${{ env.PREV_VER }} --v2 ${{ env.CURR_VER }} --fail-on-breaking

Breaking schema removals, renames (tracked via delta.columnMapping.id), narrowing type changes, or nullability tightening exit with code 2 and append a Markdown report to $GITHUB_STEP_SUMMARY.

Try it in 30 seconds: 
cargo install deltalens
# or SHA-256 verified binary (Linux/macOS):
curl -fsSL https://raw.githubusercontent.com/sandy-sachin7/deltalens/main/scripts/install.sh | bash
